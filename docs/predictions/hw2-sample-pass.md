# Registered before the pass: the HW2 blind sample on a phone

Drafted 2026-10-05 02:16 EDT. **The commit that adds this file is the registration** (`theory/RECORD-THEORY.md` section 8, step 2). Do not edit this file or the fixture after it: write a new dated registration. A test pins both (`checks/test_prediction.py`).

## The point

- **What this is.** A prediction, made before the owner's HW2 blind sample pass, of where the pass will be hard and in which order its parts will take time. The pass: 45 sampled (question, student) pairs, graded blind in TapGrade 0.6.7 sample mode on an iPhone, picks kept on the phone, exported as JSON, handed back. Nobody has used this flow on a phone yet.
- **Against which code.** speeds-kit `cec1bba`, script sha256 `730f0a93…`, 3395 lines, build 10-05 01:03. An earlier draft against `ca80695` was never registered; section "What changed in TapGrade between the first draft" says what moved since, by how much. A registration against `cac0dc8` was built and replaced before anything was pushed; the section after it says what moved since that one.
- **Seven segments, one chain each** (table below). The load model ranks one instance of each. It is ordinal: not minutes.
- **Memory is predicted to fail in one place.** Choosing chips for a part (S3 step 7, and the same step in S4 and S5). The step needs 2 slots and two items are held (what the student wrote, what the key says): working set 4 against B = 3. Everywhere else the working set fits: install peaks at 3, the queue, the export and the hand-back at 2.
- **The bank's size is not known.** The measured layout is for an invented bank of 137 chips (15 per question), a stress sample. The runbook's example output says 31 bank items (docs/HW2-HW3-RUNBOOK.md:132), 31 chips in all, so a bank of that size was measured too (section 3b): lists of 4.0 screens instead of 10.9, and a part's key in view with its chips 59% of the time instead of 29%. The memory prediction stands at both sizes and is weaker in the small one; P1, P2, P8 and P12 sit between the two.
- **Most of the friction is not memory, and no verifier reads it.** The chip window is 173 px, 20% of the screen, with no chip on the first screen; one question's list is 10.9 screens (median; 4.0 in the example-size bank). None, No deductions, the Grade button, hiding and resizing the sheet throw the list back to the top. The load toast leaving moves the content 62 px. From a pair, the Queue button is 10.3 screens down (3.4 in the example-size bank). All measured on a mock in headless Chromium.
- **The way to the first pair is in the runbook.** At `cec1bba` it names both routes (docs/HW2-HW3-RUNBOOK.md:143; docs/HW2-HW3-RUNBOOK.md:144) and says the Sample tab is not in the Grade view (docs/HW2-HW3-RUNBOOK.md:142). At `ca80695` it said "The pass: Grade, then the Sample tab, then Next pair", which sent the owner to a tab the Grade view does not have. The docs were fixed before this registration; Q1's probability fell (the section on what changed in TapGrade lists the values and why).
- **40 events, each with a step and a probability** (12 declared, 13 measured, 8 carried from HW1, 7 guessed). Top five friction events: P2 0.70; P3 0.60; P1 0.55; P7 0.55; R1 0.55. 7 of the events are predictions that nothing goes wrong (p at or below 0.10).
- **Order of durations** (one instance each): pair with a reload > pair after a lock > one pair > export = hand-back > read the queue. Install is not comparable by duration.
- **What would make it wrong** is in section 7: a tau-b of 0 or below, a pair of segments the weights order stably that the pass reverses, no better a score than counting steps, onsets that hit no more than chance, friction at steps where every verifier was silent.
- **What it is not.** Written by the same author as the chain layer, the fixture and the measurement script. The weights are ordinal and uncalibrated. The artifact was measured on a mock Canvas in headless Chromium at 390x844 touch with an invented sample, not on an iPhone. Section 8.

**Why B = 3.**

1. 3 is the checker's default (`checks/chain.py` `DEFAULT_BUDGET`, "a few", `docs/OPERATION-MODEL.md` section 3). It has been there since `65d4c1c` (2026-10-04, 14:40 ET), before the HW1 narration was transcribed into this repository (`fbc7ea3`, 17:59 ET) and before the theory fitted B on it (`b1debd5`, 18:17 ET). A registered prediction should use the value that existed before the data.
2. B = 2 is the value that fitted HW1 (`theory/RECORD-THEORY.md` section 5: 5 of 5 reported losses within or after high-pressure steps, 8 high-pressure steps away from any loss). It was chosen on that same data, and the theory says the items were encoded after the outcomes were read. It has a history, so it is not the primary here. On HW1, B = 3 caught 2 of 5 losses with 7 high-pressure steps away from any loss; B = 4 caught 1 of 5 with 4.
3. The narrator's own figure for a tired state is "3 bit" (theory section 5). Bits are not items, so this says only "small".

At B = 4 the model predicts no onset anywhere (the peak is 4). At B = 2 it adds 4 to the 4 of B = 3: S1 steps 4, 5, 11, 12. The pass will say which B it prefers. That is a finding about B, not a change to this registration.

## 6. Scoring, and what the owner is asked to leave

**The owner leaves** a narration written right after the pass, in their own words (as on 2026-10-03), and screenshots with clock times. Nothing else. Screenshots with the status-bar clock help most at: the first page after the load, the queue, a few pairs (the foot says `Recorded HH:MM`), the export, the paste into the chat. Suggested, not required: write the narration before reading section 4, which would prime it.

**Then** someone transcribes, as for HW1 (`docs/evidence/hw1-correction-2026-10-03/`), and codes an outcomes file (`emu-outcomes/1`, described in the header of `checks/prediction_score.py`) **without reading the p column**, then runs `python3 checks/prediction_score.py docs/predictions/hw2-sample-pass.prediction.json OUTCOMES.json`.

| Score | Definition |
|---|---|
| Brier | mean of (p - o)^2 over scored events. o = 1 when the observable is met, 0 when the event's segment is narrated or shown and it is not, not scored when the segment is neither. Reported overall, per basis (with how often p was on the right side of 0.5) and per segment, against the constant forecast at the mean p and against 0.5 (score 0.25) |
| Kendall tau-b | between the predicted ranks (section 5) and the measured minutes of one instance of each comparable segment (median over its dated instances, clock resolution one minute, equal whole minutes tie). Needs 4 segments with a duration. Also the exact one-sided permutation p, and the same for the step-count baseline |
| Onsets | a narrated loss (forgot, lost the goal, went back to re-read), mapped by the transcriber to a step of the chain before reading p, is a **hit** when it is within 2 steps of a predicted onset of the same chain. Scored at B = 3, and at 2 and 4. Against chance: the share of that chain's steps within 2 of an onset (5 of 9 in S3). A loss in a chain with no predicted onset is a **false alarm** |
| P-02be | the observed rate of events whose steps carry a verifier finding against events whose steps carry none; unregistered frictions (none of the 40 describes them) and whether they sit at a silent step; false findings (a finding whose step is narrated as smooth) |

What an instance is, and where its minutes come from, is in the JSON (`scoring.durations`). A gap of over 10 minutes between two saves is a break and not an instance; the time the phone is locked is removed.

## 7. What would falsify

**P-67a1, the load weights** (`docs/OPEN-PROBLEMS.md`). On this pass the weights are not supported if any of these holds:

- tau-b of the load ranking is 0 or below over the comparable segments that have a measured duration (4 are needed to score)
- any pair the weights order stably is measured the other way by at least 1 minute and 25% (kendall.reversals)
- tau-b of the step-count baseline is at least that of the load: the weights add nothing over counting steps
- Limit: the two rankings differ on 2 of 15 comparable pairs, so the third test can only fail or pass on those.

**P-02be, a chain can pass by omission.** The gap is shown on this pass if any of these holds:

- an unregistered friction sits at a step where no verifier fired (p02be.unregistered_at_a_silent_step above 0)
- a finding sits at a step the narration calls smooth (p02be.false_findings above 0)
- events at steps with no finding occur at least as often as events at steps with one (p02be: the rate without a finding is not below the rate with one)
- It is not shown, on this pass, if none of the three holds over at least 15 scored events.

**Two more from theory section 10**, scored by the same script:

- The memory model: at B=3 the narrated losses in the chains with a predicted onset hit within two steps no more often than chance gives (onsets.3: hits_within_two_steps at or below hits_expected_by_chance). The same at B=2 and B=4; B is not chosen from them.
- The measured predictors: for events with basis 'measured', p was on the wrong side of 0.5 more often than on the right side (brier.by_basis.measured: agree below half of n).

One pass by one person is weak evidence either way (theory section 8). The protocol accumulates over tasks, and each new account is held out until scored.

## 8. Limits

- Written by the same author as the builder of the chain layer, the fixture and the measurement script: not independent.
- The load weights are ordinal and uncalibrated (P-67a1); amounts, parts per pair and taps per pair are guesses.
- The pass has not happened: every p is a belief, none is fitted.
- The artifact was measured on a mock Canvas in headless Chromium at 390x844 touch with this container's fonts, not on an iPhone, not on a real Canvas, with an invented sample.
- The snapshot is speeds-kit cec1bba, the sample fixer's follow-up included; a further review round may change the sample mode again, and what it changes is not predicted here: if this registration is already pushed when it does, the new code is a new dated registration.
- HW1's outcomes are base rates only (basis carried-from-HW1): one pass by one person.
- The real bank's size is unknown: the measured layout is for an invented bank of 137 chips (15 per question), and a bank of the runbook's example size (31 bank items, docs/HW2-HW3-RUNBOOK.md:132: 31 chips in all) was measured too; events P1, P2, P8 and P12 state a p between the two.
- +-2 steps covers 5 of the 9 steps of the pair chain: a loss placed at random hits more often than not.
- Silence in a narration is ambiguous: an event coded 0 may be a difficulty that was not mentioned.
- The transcriber is the coordinating session, which has read this file: coding blind to p is a rule, not a guarantee.
- One pass by one person: the protocol accumulates across tasks, and each new account is held out until scored (theory section 8).

## Re-running on the final code

The sample fixer's follow-up is in this snapshot (Save for a student outside the sample asks; Add deduction and Add credit item hidden and the shared bank page not pushed while a sample is loaded; the runbook and `docs/TAPGRADE.md` naming the route to the queue as it is: docs/HW2-HW3-RUNBOOK.md:142; docs/TAPGRADE.md:423-435). A further review round may still change the code. Until this registration is pushed (a commit that is not pushed can be replaced), one command remakes everything that moved:

```bash
python3 -m checks.hw2_sample_prediction rebuild --speeds-kit /path/to/speeds-kit --port 8881     # about 5 minutes; reads the checkout, never writes in it
```

What it does, in order: reads the files from the checkout (and stops if they have local changes); copies the script and the mock Canvas to a temporary folder; starts the mock on the port (8881 to 8883) and stops it before it returns; measures both bank sizes; finds every line of the code and of the docs that a note or an event cites, by its anchor; rebuilds the fixture, the inputs file, the registration JSON, this file and the short section of `docs/OPERATION-CHAINS.md`; runs `bin/emu chain check`. It then prints what moved. It stops, and says so, when a cited construct or line of the docs is gone or appears twice, or when something moved since the first draft that `checks/hw2_sample_prediction/changes.py` does not explain.

What a person still does: read the notes and events the command lists (a cited construct whose first line changed; a doc or kit file that changed), edit `chains.py` where a declared property must change and `events.py` where a probability must (each event's `rests_on` says what it rests on), explain new differences in `changes.py`, and run it again until it stops with nothing to explain. Then the same command with `--commit` makes the two commits, the chains and measurements first and the registration last:

```bash
python3 -m checks.hw2_sample_prediction rebuild --speeds-kit /path/to/speeds-kit --commit --replace-previous --tests --trailer 'LINE OF THE COMMIT MESSAGE' --trailer 'ANOTHER LINE'
```

`--replace-previous` drops the last two commits only when they are the pair this command made (soft reset: the working tree is kept). Built against another speeds-kit commit, the new registration keeps the one it drops as data in `docs/predictions/replaced-<commit>/` (and removes an older such folder), so that it can say what moved since; built again against the same commit, only the text is amended and the folder of the earlier registration stays. `--tests` also runs `checks/test_chain.py`, `checks/test_explore_text.py`, `bin/gen_tree.py --check` and `checks/ci_claims.py` (port 8883). Nothing is pushed. Do not edit a registered file by hand: `python3 -m pytest -q checks/test_prediction.py` fails if the fixture, a measured file, the inputs, the generator or the registered numbers move.
